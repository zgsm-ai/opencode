将仓库探索/代码定位任务委托给 QuickExploreAgent。

当你需要像大海捞针一样定位时使用此工具：
- 某个功能在哪里实现？
- 某个路由/命令/入口点在哪里注册？
- 某个错误消息或配置键从哪里来？
- 哪个文件拥有某个类/函数，谁调用它？

重要提示：
- 如果目标文件位置已经明确（你已经有了相对于仓库的路径，或者已经将范围缩小到几个文件），请勿使用此工具。在这种情况下，直接读取/概览已知文件并继续进行更改即可。
- 仅在以下情况使用此工具：你尚不清楚文件/路径，或者你需要跨模块的入口点/注册/调用链证据来准确定位正确的位置。
- 你应该将 exploration_target（探索目标）编写为具体的定位请求，如果你有确切的字符串/符号，请一并包含在内。

## 参数说明

- **exploration_target** (必需): 单个、具体的探索/代码定位请求。
  
  仅在你不知道目标文件/路径时使用此工具（或需要跨模块的入口点/注册/调用链证据）。
  如果目标文件位置已知，不要调用此工具；而是直接读取/概览已知文件。
  
  编写方式应使 agent 能可靠地搜索：
  - 如已知，包含精确符号（函数/类/模块名）
  - 如相关，包含精确字符串（UI 文本、错误消息、配置键、路由路径）
  - 包含期望的输出形式（例如"返回文件路径 + 符号名 + 关键证据"）
  
  好的示例：
  - "定位 'execute_quick_explore_task' 在哪里注册以及它如何创建 QuickExploreAgent。返回文件路径 + 关键函数。"
  - "查找路由 '/api/v1/login'（或类似）的处理器。提供入口点注册和最终处理器实现。"
  - "搜索错误消息 'Git Bash not found on Windows system' 并定位引发它的代码。"
  - "QuickExploreAgent 类在哪里定义，它如何加载提示模板？"
  
  差的示例：
  - "打开文件 X 并更改 Y"（路径已知；这不是探索）
  - "探索项目"（太宽泛）
  - "查找 auth"（太模糊）

## 使用示例

```json
{
  "tool": "quick_explore",
  "arguments": {
    "exploration_target": "定位 'execute_quick_explore_task' 在哪里注册以及它如何创建 QuickExploreAgent。返回文件路径 + 关键函数。"
  }
}
```

## 与 task 工具的对比

此工具是调用 `task` 工具并设置 `subagent_type="quick-explore"` 的**推荐替代方案**。

关键区别：
- **严格验证**：参数使用 Zod schema 进行验证
- **结构化目标**：探索目标以结构化字符串传递，而非自由文本
- **更好的错误消息**：清晰的验证错误指导 LLM 修正参数

## 执行流程

1. 调用 Agent（如 ProposalAgent）调用 `quick_explore` 工具，传递 exploration_target
2. 系统验证参数
3. 创建 QuickExploreAgent 的独立 Session（只读权限）
4. QuickExploreAgent 执行探索任务
5. 完成后返回结构化的探索结果

## 注意事项

- QuickExploreAgent 禁止修改任何代码（只读权限）
- 禁止启动其他子 Agent
- 完成探索后必须调用 `sub_agent_task_done` 工具返回结果
