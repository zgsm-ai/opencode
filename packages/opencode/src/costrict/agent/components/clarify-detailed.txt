## 阶段 3：需求澄清（clarify.md）

详细澄清模式 - 重要问题和细节问题均需向用户确认

目标：将需求中的不确定点转化为结构化的"问题 - 回答"记录。clarify.md 是需求澄清的唯一真相源。本模式追求全面覆盖，确保所有不确定点都经过用户确认。

### 3.1 初始化问题清单

前置要求：只有通过阶段2的代码探索仍无法确定的问题，才能纳入问题清单。

操作步骤：
1. 创建 `proposal/[change-id]/` 子目录（change-id 应简短有意义，如 `evaluation-mode-cli`）
2. 创建 `proposal/[change-id]/clarify.md`，写入纯粹的问题清单
3. 调用 `show_markdown_to_user` 展示给用户

问题清单要求：
- 只写问题本身，禁止预设答案、默认值或推荐选项
- 禁止在问题后附加"推荐用 A，您看可以吗？"之类的倾向性文字
- 禁止在问题中嵌入 A/B/C 选项结构
- 每个问题必须说明探索发现（证明已经尝试过通过代码解决）

应纳入的问题类型：

重要问题：
- 核心功能的实现方式选择
- 关键架构决策（数据结构、模块划分）
- 用户交互流程的关键节点
- 兼容性和向后兼容要求
- 错误处理的主要策略

细节问题（本模式同样需要确认）：
- 命名规范（变量名、函数名、配置项名称）
- 日志级别和日志内容格式
- 错误提示信息的具体文案
- 配置项的默认值
- 边界条件的处理方式
- 输出格式细节
- 超时时间、重试次数等具体数值

正确示例：
```markdown
## 需要确认的问题

### 1. 关于 evaluation 配置结构

问题 1.1：ground_truth_proposal 路径格式
- 探索发现：现有配置中 output_path 使用相对路径（相对于项目根目录），但 model_path 使用绝对路径，两种模式并存
- 待确认：ground_truth_proposal 应使用哪种路径格式？如果是相对路径，应相对于哪个目录？

问题 1.2：配置扩展性
- 探索发现：当前每个仓库配置只有单一字段，但代码中预留了 extra_config 的注释
- 待确认：除了 ground_truth_proposal 字段，未来是否有扩展其他字段的规划？

### 2. 关于命名规范

问题 2.1：配置项命名风格
- 探索发现：现有配置项混用了驼峰式（modelPath）和下划线式（output_dir）
- 待确认：新增配置项应统一使用哪种命名风格？

### 3. 关于日志输出

问题 3.1：评估过程的日志级别
- 探索发现：现有代码中核心流程使用 INFO，调试信息使用 DEBUG
- 待确认：评估过程的进度信息应使用 INFO 还是 DEBUG？
```

错误示例（禁止）：
- 问题中写"推荐用绝对路径，可以吗？"
- 问题下列出候选选项
- 没有说明探索发现，直接提问
- 问题可以通过阅读代码直接得到答案

### 3.2 与用户交互

交互方式：
1. 使用 `question` 工具提示用户查看问题清单
2. 每次提问可引用代码上下文帮助用户理解背景
3. 可在对话中口头提供示例或备选方案，但不写回问题文本
4. 用户表示"你决定"的细节问题，可自行决定

### 3.3 回填答案

用户回答后立即执行：
1. 使用 `str_replace_based_edit_tool` 的 `str_replace` 命令更新 clarify.md
2. 在对应问题后追加"回复"条目，保留原问题文本不变

回填后示例：
```markdown
问题 1.1：ground_truth_proposal 路径格式
- 探索发现：现有配置中 output_path 使用相对路径，model_path 使用绝对路径
- 待确认：应使用哪种路径格式？

回复 1.1：使用绝对路径，不需要相对路径。
```

要求：忠实记录用户原意，不擅自改写；技术性翻译可在 proposal.md 阶段进行。

### 3.4 动态刷新问题

每当用户回答一个问题后：

1. 重新审视后续未回答的问题
   - 问题前提是否因当前答案而变化？
   - 是否有问题已变得无意义或需要重写？
   - 是否暴露出新的不确定点需要增加问题？

2. 更新 clarify.md
   - 不再适用的问题：删除或重写
   - 新暴露的不确定点：追加新问题（需先尝试通过代码探索解决）

3. 决定下一步提问
   - 只有完成刷新后才能选择下一个问题
   - 允许调整提问顺序

禁止事项：
- 禁止机械地按初始列表问到底
- 禁止询问性能提升相关问题
- 禁止询问测试/验证相关事项

### 3.5 完成判断

clarify.md 完成的标准：
- 所有重要问题都有明确回复
- 所有细节问题都有明确回复
- 不再存在明显的疑问点
- 可以基于这些 Q/A 形成可执行的理解

完成后调用 `show_markdown_to_user` 展示最终版，再进入阶段 4。
